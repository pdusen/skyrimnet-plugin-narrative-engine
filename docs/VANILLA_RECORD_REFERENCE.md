# Vanilla record reference

Every record in retail Skyrim SE — base game plus all three DLC — is available locally as a
[Spriggit](https://github.com/Mutagen-Modding/Spriggit)-serialized YAML tree at:

```text
C:\Projects\spriggit-output\
```

**Use it instead of guessing.** Any question of the form "does `<EditorID>` exist?", "what FormID is X?", "what flags
does that vanilla package have?", "which factions does this NPC belong to?", "what conditions does that quest alias
use?" is answerable by reading files in that folder. Never answer such a question from memory, and never invent an
EditorID or FormID for a vanilla record — look it up.

Roughly 234,000 YAML files, ~3.5 GB total. The tree lives **outside** the repo and is not version controlled — it is
local machine state, regenerated by `C:\Projects\spriggit-output\export-esms.ps1` (incremental; re-serializes a plugin
only when its ESM hash or the Spriggit package/version changes). Serialized with `Spriggit.Yaml.Skyrim` 0.40.1,
game release `SkyrimSE`.

## Layout

Each plugin folder holds one subfolder per record type, named for the Mutagen group (`Factions/`, `Packages/`,
`Quests/`, `Npcs/`, `Keywords/`, `Locations/`, `Spells/`, `MagicEffects/`, `FormLists/`, `Globals/`, `Scenes/`,
`DialogTopics/`, `StoryManagerEventNodes/`, …). `Skyrim/` has 113 such folders.

Flat record types are one file per record, named `<EditorID> - <FormID>_<SourcePlugin>.esm.yaml`:

```text
Skyrim/Factions/BanditFaction - 01BCC0_Skyrim.esm.yaml
Skyrim/Packages/WhiterunKidFightSceneBraithTravel - 10DE9F_Skyrim.esm.yaml
```

The FormID in the filename is the **load-order-independent** ID (`01BCC0`), without the mod index byte. Records with
no EditorID are named by FormID alone.

Nested record types are directories with a `RecordData.yaml` inside:

- `Cells/` — bucketed by group into `Cells/<block>/<subblock>/<EditorID> - <FormID>_<plugin>.esm/RecordData.yaml`
- `Worldspaces/` — `Worldspaces/<EditorID> - <FormID>_<plugin>.esm/<x>, <y>/…`, with the worldspace's own record in
  `RecordData.yaml` at its root
- Plugin-level metadata: `<Plugin>/RecordData.yaml` (mod header, masters) and `<Plugin>/spriggit-meta.json`

**Override records keep the original master's name.** A record defined in `Skyrim.esm` but overridden by
`Dragonborn.esm` appears under `Dragonborn/` still suffixed `_Skyrim.esm.yaml` — e.g.
`Dragonborn/Packages/defaultHoldPositionLinkedRef512WithTravel - 101C01_Skyrim.esm.yaml`. So the same EditorID can
match in several plugin folders; the winning version is the one from the plugin latest in load order
(Skyrim → Update → Dawnguard → HearthFires → Dragonborn).

## Record format

Plain YAML, one record per file, field names matching Mutagen's record schema:

```yaml
FormKey: 01BCC0:Skyrim.esm
VersionControl: 3499787
EditorID: BanditFaction
FormVersion: 37
Relations:
  - Target: 109ACF:Skyrim.esm
    Reaction: Ally
Flags:
  - HiddenFromPC
  - CanBeOwner
```

Cross-references are `FormKey`s (`<FormID>:<SourcePlugin>`), not EditorIDs — to follow a reference, search for the
FormID.

## How to search it

**By EditorID — use Glob, not Grep.** The EditorID is in the filename, so a glob is dramatically faster than
grepping 3.5 GB:

```text
Glob: */Packages/*Travel*.yaml          path: C:/Projects/spriggit-output
Glob: Skyrim/Factions/Bandit*.yaml      path: C:/Projects/spriggit-output
```

**By FormID:**

```text
Glob: */**/* - 01BCC0_*.yaml            path: C:/Projects/spriggit-output
```

**By field content — always scope the path to one record-type folder**, never the tree root:

```text
Grep: CanBeOwner    path: C:/Projects/spriggit-output/Skyrim/Factions
```

**Files are CRLF.** A trailing `$` anchor will not match, because the line ends `\r\n`. Write `^EditorID: Foo\r?$`
or just drop the anchor. This bites silently — the search returns "no matches" rather than an error.

## What it is and isn't authoritative for

**Authoritative for:** what records exist in retail Skyrim SE + DLC, their EditorIDs, FormIDs, field values, flags,
conditions, and cross-references. If a claim about vanilla content contradicts this tree, this tree wins.

**Not a source for:**

- **Anything not in the five vanilla masters** — no Creation Club content, no USSEP or other patches, no third-party
  mods. Absence here means "not in vanilla," not "doesn't exist on the user's setup." (The export runs against the
  NGVO Stock Game `Data` folder, but only serializes the five vanilla `.esm` files.)
- **Runtime behavior** — the data says what a package or quest *is*, not how the engine executes it. For that, use
  CommonLibSSE-NG headers, in-game testing, and `docs/engine-findings/`.
- **CK UI semantics** — how a field is labeled in the Creation Kit, or whether a checkbox exists, is a CK Wiki
  question; this tree gives the serialized data model, which doesn't always map 1:1 to the CK's presentation.
